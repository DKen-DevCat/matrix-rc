# 通信プロトコル（v1）

設計書①6章「通信の約束ごと」を、バイト列として固定したもの。Phase 1-a／1-b／2 で同じものを使う（1-b からは UDP の外側を DTLS-PSK で包むだけで、中身は変えない）。

実装は `web/js/protocol.js`（ブラウザとサーバが共用）と `firmware/lib/core/protocol.h`（機体）の2か所。両者の一致は、同じテストベクタ（下の「テストベクタ」）を双方のテストで検証して保証する。

## 経路

```
ブラウザ ──WebSocket(バイナリ)──▶ サーバ ──UDP──▶ 機体      CONTROL（50Hz）
ブラウザ ◀─WebSocket(バイナリ)── サーバ ◀─UDP── 機体      TELEMETRY（10Hz）／VIDEO／AUDIO
                                  サーバ ◀─UDP── 機体      HELLO（1Hz。登録と NAT 維持）
```

- 機体は自分から HELLO を送ってサーバに登録する。サーバは HELLO の送信元アドレスにだけ CONTROL を送る。機体はサーバのアドレス以外から届いたパケットを捨てる（待ち受けポートを外に開けない）。
- サーバは CONTROL を補完しない。ブラウザから届いたバイト列を検査（長さ・種別・機体ID・操作権）して、そのまま機体へ送る。
- 認証は Phase 1-a では共有トークン（ブラウザは WebSocket の最初のテキストメッセージ、機体は HELLO に入れる）。

## 共通ヘッダ（4 バイト）

すべて little endian。

| オフセット | 型 | 内容 |
|---|---|---|
| 0 | u8 | マジック `0x4D`（'M'） |
| 1 | u8 | バージョン `1` |
| 2 | u8 | 種別（1=CONTROL, 2=TELEMETRY, 3=HELLO, 4=VIDEO, 5=AUDIO。6=FRAME_META は予約、末尾の節） |
| 3 | u8 | 機体ID（1〜254） |

## CONTROL（20 バイト、ブラウザ→機体）

| オフセット | 型 | 内容 |
|---|---|---|
| 4 | u32 | セッションID（ブラウザの接続ごとに乱数。0 は使わない） |
| 8 | u32 | 連番 seq（セッション内で 1 ずつ増える） |
| 12 | u32 | 送信時刻（ブラウザの `performance.now()` の ms、下位 32 ビット） |
| 16 | u8 | キー（bit0=W, bit1=A, bit2=S, bit3=D, bit4=Space） |
| 17 | u8 | 予約（0） |
| 18 | u16 | ジャンプID（0=なし。Space を押すたびに 1 増やし、0 は飛ばす） |

機体の受け付け規則：

- 現在のセッションと同じセッションIDで、seq が最後に採用したものより大きいものだけを採用する。
- 違うセッションIDのパケットは、機体が停止中（300ms 以上採用していない）のときだけ受け入れ、新しいセッションに切り替える。走行中に別のセッションが割り込むことはない。
- ジャンプは「前回と違う 0 以外のジャンプID」を受けたときに 1 回だけ実行する。セッションが変わったら前回のジャンプIDを忘れる。
- 300ms 採用しなければ、走行もジャンプも止める。

## TELEMETRY（28 バイト、機体→ブラウザ）

| オフセット | 型 | 内容 |
|---|---|---|
| 4 | u32 | 最後に採用したセッションID |
| 8 | u32 | 最後に採用した seq |
| 12 | u32 | そのパケットの送信時刻（そのまま返す。ブラウザが今の時刻との差を取って往復遅延にする） |
| 16 | u16 | 電池電圧（mV） |
| 18 | u8 | 状態フラグ（bit0=停止中, bit1=チャージ済み, bit2=低電圧の警告, bit3=低電圧で停止, bit4=ジャンプ機構の異常, bit5=撮影中） |
| 19 | i8 | 受信強度（dBm） |
| 20 | u16 | 最後に受け付けたジャンプID（ブラウザはこれで届いたことを確かめる） |
| 22 | u8 | ジャンプの状態（0=不明, 1=チャージ中, 2=チャージ済み, 3=発射中, 4=異常） |
| 23 | u8 | 最後の CONTROL を受け取ってからの時間（ms、255 で頭打ち）。ブラウザは往復遅延からこれを引く |
| 24 | u32 | 起動からの時間（ms） |

## HELLO（20 バイト、機体→サーバ）

| オフセット | 型 | 内容 |
|---|---|---|
| 4 | 16 バイト | 共有トークン（UTF-8、16 バイトに満たなければ 0 埋め） |

## VIDEO（8＋最大 240 バイト、機体→ブラウザ）

JPEG 1 枚を 240 バイトずつに分けて送る。240 は Phase 2 の ESP-NOW（1 パケット 250 バイト）にそのまま載せるための値。

| オフセット | 型 | 内容 |
|---|---|---|
| 4 | u16 | フレーム番号 |
| 6 | u8 | 分割の番号（0 から） |
| 7 | u8 | 分割の総数 |
| 8 | 〜240 バイト | JPEG の断片 |

受け側は全部そろったフレームだけを表示する。新しいフレーム番号の断片が来たら、そろっていない古いフレームは捨てる（溜めない）。

## AUDIO（8＋最大 240 バイト、機体→ブラウザ）

| オフセット | 型 | 内容 |
|---|---|---|
| 4 | u16 | 音声の連番 |
| 6 | u16 | 予約（0） |
| 8 | 〜240 バイト | 16kHz・16 ビット・モノラルの PCM（120 サンプル＝7.5ms） |

録音はしない。サーバもブラウザも保存せず、再生するだけ。

## 予約：FRAME_META（種別 6、技術検証枠・未実装）

設計書④ E2（動画生成 AI によるラグ隠し）で使う予定の種別。ブラウザが「この映像には、どの操作まで反映されているか」をフレームごとに知るためのもの。機体→ブラウザで、各フレームの最初の VIDEO 断片の直前に送る。種別を足すだけで VIDEO の形は変えない。

| オフセット | 型 | 内容 |
|---|---|---|
| 4 | u16 | フレーム番号（続く VIDEO と同じ） |
| 6 | u16 | 予約（0） |
| 8 | u32 | 撮影時刻（機体の起動からの ms。TELEMETRY の「起動からの時間」と同じ時計） |
| 12 | u32 | 撮影の時点で採用していたセッションID |
| 16 | u32 | 撮影の時点で最後に採用していた CONTROL の seq |

計 20 バイト。起動後まだ CONTROL を採用していなければ、セッションIDと seq は両方 0（CONTROL のセッションIDは 0 を使わず、seq は 1 から始まるので「なし」と区別できる）。

ブラウザは送った CONTROL を「seq → キー・送信時刻」で覚えておき、次の2つに使う。

- 表示の遅れ ＝ 今 − その seq の送信時刻（PC と機体の時計を合わせなくてよい。操作の上りと映像の下りを合わせた「キーを押してから画面に出るまで」の遅れになる）
- 予測の作り直し：届いた本物のフレームを起点に、その seq より後の入力だけで「今」の映像を予測し直す

決まりごと：

- 「直前に送る」は送る順で、届く順ではない（UDP は順序を保証しない）。ブラウザは到着順ではなくフレーム番号で VIDEO と対応付け、対応する VIDEO がそろわずに捨てられたフレームの FRAME_META も捨てる。
- セッションIDが自分のものと違うフレーム（別の操作者の操作や、接続し直す前の操作が反映された映像）は、遅れの計算にも予測の起点にも使わない。
- 今の v1 の実装への影響：ブラウザ（`web/js/app.js`）は知らない種別を無視し、サーバ（`server/src/relay.js`）は機体からの TELEMETRY・VIDEO・AUDIO 以外をブラウザへ転送しないので、機体が送り始めても何も壊れない。実装するときは、機体（送信）・サーバ（転送する種別に 6 を足す）・ブラウザ（受信）の3か所を変える。
