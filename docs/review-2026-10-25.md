# 計画・設計書レビュー（2026-10-25）

対象：README、CLAUDE.md、Notion の企画まとめ・部品表・設計書①②③、図面 W1〜W3／C1〜C4／R1〜R3 とその生成スクリプト。
末尾の「反映状況」に、このレビューで Notion と図面に反映した内容と、判断を残した項目をまとめた。

## 結論

計画と設計書の骨格は堅実で、通信プロトコルの考え方（機体から接続・キー状態 50Hz・連番・300ms 停止・ジャンプ ID）は良くできている。C4 のジャンプ計算（エネルギー・運動量・トルク）も検算して一致した。

一方で、設計書②の「3cm の段差をジャンプで越える」が現状の寸法では成立しない。暗号化・ピン拡張・LTE 基板サイズの 3 つにも設計上の穴がある。ドキュメント間の不整合も数か所あった。Phase 1-a の着手自体は問題ないが、1-b に進む前に A-1〜A-5 を解消する。

## 全体像

この企画は「操作の確実性（300ms 停止）」を最優先にし、映像は劣化を許容する設計である。その軸はすべての設計書で一貫しており、これが最大の強み。

リスクは機械系と 1-b に集中している。1-a は Wi-Fi と机上なので失敗コストが低い。一方 1-b では「LTE 化」「名刺サイズ化」「ジャンプ本番」という 3 つの未知を同時に抱えていた。企画まとめ 7 章にあった「大きめの台車で屋外走行」の段階が設計書から消えていたことが原因で、今回 1-b を 1-b1／1-b2／1-b3 に分けた。

## A. 設計の成立に関わるもの（1-b の前に解消）

### A-1. 段差越えは鉛直高さだけでは足りない

C4 は跳躍高さ 4〜6cm しか見積もっていない。3cm の段差に両軸を乗せるには、3cm より高い滞空中にホイールベース 61mm 以上前進する必要がある。

| 項目 | 値 |
|---|---|
| 下段を引き上げた後の初速 | 約 1.1 m/s（C4 と一致） |
| 高さ 3cm 以上にいる時間 | 約 0.16 秒 |
| 走行速度（N20 300rpm@6V を 3.7V 駆動、φ26） | 約 0.25 m/s |
| 滞空中の前進距離 | 約 4cm |
| 必要な前進距離 | 61mm ＋余裕 → 約 0.5 m/s 必要 |

対策は、ばね軸を前傾させて水平速度成分を作る、または走行モーターを 500rpm 級にする。Phase 1-b2 の試験は「鉛直高さ」ではなく「助走付きで段差を越える」で行う。

### A-2. ばねとカムの寸法が C3 と両立しない

- 部品表のばね（自由長 15mm、線径 0.5〜0.6、外径 5〜6）で 0.5N/mm を出すには約 15 巻きが必要で、密着高さは約 9mm になる。15mm から 10mm は縮められない。自由長 25mm 以上にするか、線径を太くして巻数を減らす。
- C3 の上下段すき間は 12mm で、縮めると 2mm になる。10mm リフトの渦巻きカムは直径 30mm 級になり、12mm 厚の下段にも 2mm のすき間にも収まらない。C3 に「縮めた状態」の側面図とカムの収まり場所を描いて確定する。てこで 2 倍に増幅して小さいカムを使う案も検討する。

### A-3. AES-GCM の自前実装はノンス再利用の危険がある

機体ごとの固定鍵で、再起動後に連番が 0 に戻ると同じノンスを再利用する。GCM でこれが起きると認証が破れ、平文も漏れる。起動ごとにセッション鍵を作るハンドシェイクを入れるか、ESP-IDF 標準の mbedTLS で DTLS-PSK を使う。後者のほうが安全で実装も少ない。

あわせて、ブラウザ再読込や機体再起動で連番が巻き戻ったときの扱い（セッション ID の付与）が未定義だった。

### A-4. U137 追加のためのピン確保策が成立しない

設計書①は「I2C の GPIO 拡張で確保」としていたが、11 ピンすべて使用済みなので I2C 自体の 2 ピンがない。U137 は UART なので拡張 IC 経由でも動かない。

案：カム位置スイッチを廃止してモーター電流か時間で「チャージ完了」を検知し、U137 内蔵の GNSS で MAX-M10S を置き換え、空いた D8 と D9 を U137 の UART に充てる。

### A-5. LTE 基板のサイズとアンテナ効率が 1-b の最大リスク

Quectel の評価ボードは 100mm 級で名刺サイズに載らない。代替の「モジュール＋自作キャリア基板」は LCC パッケージのはんだ付けが必要で、初めてのハード開発には重い。さらに 800MHz 帯のアンテナは波長の 4 分の 1 が約 9cm で、91mm の筐体ではグランドが足りず効率が落ちる。床すれすれという不利に上乗せされる。

1-a と並行して評価ボードを入手し、床置きで実測して方針を決める。

## B. 計画の構成

- **B-1. 段階の番号体系が 3 種類あった。** 企画まとめは段階①〜④、部品表は区分 A/B/C と①②③、設計書は Phase 1-a/1-b/2。「Phase 1-a／1-b1／1-b2／1-b3／2」に統一した。
- **B-2. 1-b を 3 つに割る。** 1-b1＝W3 の車台のまま LTE＋VPS＋GPS に載せ替える、1-b2＝ジャンプ機構の単体試作、1-b3＝名刺サイズに統合。企画まとめ 7 章の方針どおりになり、不具合の切り分けが容易になる。
- **B-3. ジオフェンス停止は屋内で誤動作する。** 屋内では GPS が数十 m 飛ぶため、店内で突然止まる恐れがある。衛星数と HDOP の条件とヒステリシスを付ける。
- **B-4. Phase 2 の合格基準を見直す。** 弱い LTE で増えるのは主にパケットロスと途絶で、遅延差は R3 ほど開かない可能性がある。「300ms 停止の発生回数」と「到達率」を主指標にする。
- **B-5. ESP-NOW での映像中継は分割設計が要る。** ペイロード上限は 250 バイト（新しい ESP-IDF の v2 で約 1.4KB）。JPEG フレームの分割と再構成、欠けたフレームの破棄を設計書③に明記する。

## C. ドキュメントの不整合

- **C-1.** 企画まとめ 4 章が WebRTC・ハードウェアエンコード・B フレームなしと書いていたが、設計書は WebSocket と MJPEG。ESP32-S3 に H.264 エンコーダはないので企画まとめ側が古い。
- **C-2.** 企画まとめ 6 章の「目立つ色とブザー」は、3 章と設計書の「ブザーは付けない」と矛盾。
- **C-3.** C2 図面の電池が「1000mAh」のままだった（設計書②は 600〜800mAh 高放電）。`d1.w2(lte=True)` で電池の描画を共有していたため。
- **C-4.** 部品表 A に WS2812B 直列の 330Ω、XIAO 電池パッドへの JST-PH ピグテール、1-a の動作確認用カムがなかった。100kΩ は合計 3 本必要。
- **C-5.** 細部：C1 の「AES-GCM で暗号化」ラベルがサーバ枠に重なる。W3 のボールキャスター破線がブレッドボードの下に隠れる。`lib.py` の `label_bg` 先頭の幅計算は死にコード。`render.sh` は macOS 専用。

## D. 電源と運用

- **D-1.** XIAO の充電電流は約 100mA の仕様で、1000mAh の満充電に約 10 時間かかる。会場運用には外部の 1S 充電器と予備電池が必要。
- **D-2.** 低電圧のしきい値が未定義。保護回路のカットオフは 2.5〜3.0V で低すぎ、LTE の 2A バーストで 3.3V レギュレータがブラウンアウトする。警告 3.5V、停止 3.3V を目安にする。ADC 入力には 0.1µF を並列に入れる。
- **D-3.** 300ms 停止の前提として、サーバは状態を補完せず素通しする旨を明記する。試験に「ブラウザのタブを固まらせる」を追加。往復遅延は時計が同期していないので、機体がタイムスタンプをエコーする形にする。
- **D-4.** 上段を密閉すると XIAO はストリーミング中に 60℃を超え、LTE も発熱する。通気を考慮する。

## 良い点

機体から接続のみ・技適縛り・録画しない方針の一貫性、「探す」を使わない論証の丁寧さ、ピン割り当ての全モデル共通化、C4 の運動量計算の正確さ。
